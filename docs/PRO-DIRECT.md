# ETPH Pro bought directly (copies not installed from Google Play)

Owner decision 2026-11-24: sell ETPH Pro (US$15 one-time, same as on Play) to people who installed ETPH outside
Google Play: the APK from errant.solutions (`/download/etphonehome/<tag>/`), the GitHub release, adb. Play-installed
copies keep Google Play Billing only (Play payments policy); see `docs/pro.md` "Where Pro is bought" for the
installer check (`InstallChannel`). Desktop and router clients have nothing to license: Pro is enforced on the phone
only (`docs/pro.md`), so they need no key.

## Purchase flow

1. App (DIRECT copy) > Upgrade to Pro > **Buy ETPH Pro (US$15, one time)** opens
   `https://errant.solutions/etphonehome/pro/` in the browser (`BuildConfig.PRO_BUY_URL`, gradle `-PproBuyUrl`).
2. The page's Buy button POSTs `/api/pro/checkout`; the `errant-pro` service (ctg-infrastructure
   `services/errant-pro`) creates a Stripe Checkout Session on Errant Solutions' Stripe account (mode `payment`, the
   ETPH Pro price, metadata `app=etph-pro`, the EU/UK withdrawal-waiver consent box) and redirects to Stripe.
3. After payment Stripe returns to `/etphonehome/pro/key?s=<session>`: the page shows the license key **once**
   (issuing it itself if the webhook is not in yet) with Copy and "Activate on this phone". The key is also emailed
   (Resend, `ETPH Pro <no-reply@errant.solutions>`, reply-to support@).
4. `checkout.session.completed` / `checkout.session.async_payment_succeeded` webhooks issue the key too; the
   signature is checked (`Stripe-Signature`, 5 min tolerance) and issuance is idempotent per event and per session,
   so replays and the success page racing the webhook give one key and one email.
5. In the app: **Enter license key**, paste, **Activate** (or the link `etph://activate?key=...`, via
   `/etphonehome/pro/activate#<key>`, which opens a prefilled confirm dialog). Lost key:
   `/etphonehome/pro/#recover` emails every active key of that address again (same answer whether or not it
   bought; 3 per address per hour).

## License key

`ETPH1.<base64url(payload)>.<base64url(Ed25519 signature)>`, signature over `etph-license-v1.` + the payload part.
Payload: `{"v":1,"prod":"etph-pro","id":"EP-XXXXXXXXXX","eh":"<16 hex>","iat":"YYYY-MM-DD","mode":"live"}`:
product, purchase id (`comp-YYYYMMDD-N` for complimentary keys), email fingerprint (first 16 hex of
HMAC-SHA256(server secret, lowercased email); the server keeps only the full HMAC, never the address after the key
mail went out), issue date, mode.

- Verified offline in `android/core/.../pro/LicenseVerifier.kt` (Bouncy Castle Ed25519, already shipped for TLS).
  Public keys are committed: `android/app/pro-license-live.pub` (every build) and `pro-license-test.pub` (debug/QA
  builds only, for Stripe test-mode purchases); a test key never unlocks a release build. Several keys per mode
  are accepted (`BuildConfig.PRO_LICENSE_KEYS`), for rotation.
- Pasted keys are cleaned up (line breaks from mail programs, quotes, the whole activation URL).
- Private keys: crystalcave `~/.hermes/state/etph-pro-license-{live,test}.key` (0600) and the service's secret
  file on ollivanders. Server and app share test vectors (`android/core/src/test/resources/pro-license-vectors.txt`,
  generated by the service's tests).

## Entitlement (core `EntitlementEngine`, extended, not forked)

DIRECT copies (`Pro.directPurchaseAvailable` = not Play-installed and `BuildConfig.DIRECT_PRO`) build the engine
with a `LicenseVerifier`; Play-installed copies and the Play bundle don't, so a stored key does nothing there.

- `activate(key)`: verify, refuse ids on the known revocation list, store (`ProStore`, SharedPreferences) ->
  `Status.PRO_LICENSE`. Same Pro features as a Play purchase (Wi-Fi/Bluetooth, routers, several computers,
  auto-start + reconnect, data usage/limits): `isPro` is all that `ProGate` looks at.
- Revocation: `GET https://errant.solutions/api/pro/revocations` (`BuildConfig.PRO_REVOCATION_URL`) returns
  `ETPHREV1.<payload>.<sig>` (signed over `etph-revocations-v1.` + payload; `{"v":1,"prod","mode","iat","ids":[]}`).
  The app fetches it on app start / Start / Pro screen when the last check is a day old, applies it only if it
  verifies for the key's mode and is not older than the kept one (no rollback). A refund (full `charge.refunded`),
  a chargeback (`charge.dispute.created`; reinstated if the dispute is won) or an admin revoke puts the id on it.
- Activation signal (0.9.6+): the same request carries `?id=<license id>&v=<app version>` (`EntitlementEngine.revocationUrl`).
  The id is the public purchase id from the key's payload (`EP-...` / `comp-YYYYMMDD-N`), never the key, no device id.
  errant-pro records first_seen / last_seen / count / app version on that license row (only for ids it issued); admin query:
  `~/.hermes/scripts/pro-key-status.py <id|text from the comp reason>` on crystalcave. Older apps just don't report
  (their requests show up only in the web server log as `ETPH/<ver> (Android)`). Nothing is sent when no key is stored.
- Offline grace: the key keeps Pro offline; after 60 days without one successful check (or since activation) it
  waits for one check ("connect this phone to the internet once so ETPH can re-check it"). Play's own offline grace
  is 30 days; keys are more lenient because the phone is often the only uplink.
- Removing the key: Pro screen > Remove license key.

## Builds and policy

- `publish-play.yml` builds the bundle with `-PdistChannel=play` -> `BuildConfig.DIRECT_PRO=false`: no Buy link and
  no key entry in anything Google Play distributes, even if Android misreports the installer.
- APK releases (`release.yml`, `assembleRelease`) use the default `distChannel=direct`.
- URLs and the shown price are gradle properties (`proBuyUrl`, `proRecoverUrl`, `proRevocationUrl`,
  `proDirectPrice`), defaults = the real errant.solutions endpoints.

## Comp keys and admin

On ollivanders: `docker exec errant-pro python3 /opt/errant-pro/errant_pro.py comp --reason "..." [--email a@b]`
prints the id and key (logged as `AUDIT`, stored with its reason, revocable like any key);
`... revoke <id> --reason ...`, `... unrevoke <id>`, `... list`.
